# Architecture

```text
              network                         this machine
        ┌───────────────┐   ┌──────────────────────────────────────────────┐
        │               │   │                                              │
        │   provider    │◄──┤  sync engine ──────► store (SQLite) ───► UI  │
        │  (any backend)│──►│   · refresh              ▲   │               │
        │               │   │   · event loop           │   └─ change       │
        └───────────────┘   │   · outbox worker ───────┘      notifications│
                            │   · history paging                           │
                            └──────────────────────────────────────────────┘
```

One rule shapes everything: **the UI only reads the local store.** It never calls a provider and never waits on the network. Opening a chat, scrolling, searching and switching accounts are local queries. A background engine is the only thing that talks to a provider, and all it does with the answers is write them to the store.

## Crates

**`client-provider`** defines the `Provider` trait, the neutral model (`Account`, `Chat`, `Message`, `Contact`, ids, `DeliveryStatus`), `Capabilities`, `ProviderEvent` and `ProviderError`. It has no I/O. Adapters depend on this crate and nothing else of ours. [PROVIDERS.md](PROVIDERS.md) is its manual.

**`client-core`** is everything between a provider and the UI:

- `Store`: SQLite through `rusqlite` (bundled SQLCipher, WAL). The file on disk is encrypted; `Store::open` takes the key as a parameter and knows nothing about where it is kept (see "The database on disk"). Accounts, chats, messages, reactions, contacts, the outbox, and an FTS5 index over message text for search. Reads use their own connection, so a view never waits behind a write. The schema is versioned in `PRAGMA user_version` (v13 now: v4 files on their way out, v5 message extras, v6 profiles and groups, v7 one person under several ids, v8 how long each send took, v9 the sticker and GIF library, v10 the stickers already in the chats, v11 stories, v12 when a chat was pinned and the message a library sticker was seen in, v13 the community a group is linked to) and migrated at open (`migrations.rs`). The chat list is pinned chats first, the last one pinned on top (the provider's time, `Chat::pinned_at`, or the moment the pin was made here; a pin without a known time after those with one), then the most recently active.
- Every write emits a `StoreChange` (which account, which chat). Views subscribe and re-query what they show. The notifications are hints, not data; a listener that falls behind is told to refresh everything.
- `SyncEngine`: a refresh (accounts and chat lists: one request for the accounts and one per page of chats, nothing per chat; then one listing of the groups of each connected number, see "Communities"), a background history loader (below), an event loop that applies `ProviderEvent`s and resubscribes with backoff when the stream ends, the outbox worker, and on-demand paging of older history. Changes to a chat's state (pin, mute, archive, mark as unread) are written to the store at once and offered to the provider in the background, retried with backoff while the failure is transient and undone only if the provider refuses.
- The outbox, below.

**`provider-mock`** and **`provider-wuapi`** are two providers. The mock holds a seeded world in memory and plays the other side of conversations; the UI runs on it with `--provider mock` and the tests use it. The wuapi adapter calls the API through `wuapi`, the Rust SDK generated from its OpenAPI spec (the real chat list, with unread counts, pins and saved names, since SDK 0.6.0), and adds what a chat client needs on top: the mapping to the neutral model, the transient-or-terminal classification of errors, the two steps of the browser sign-in, the keychain, and the live transport: wuapi Streams (a connection the client opens, over server-sent events) where the deployment has it, polling where it does not. `--live auto|stream|polling` chooses (`auto` by default); the engine sees one `EventStream` either way.

**`brand-mark`** is the animated wuapi mark as a GPUI element: it blinks and looks around as it does on the wuapi site, and is still whenever it is told to be.

**`updater`** is the self-update, with no window in it: the signed release manifest, the download, the staging area, the swap of the executable (or the macOS bundle) at the next start, and putting the previous version back when the new one does not come up. **`xtask`** is the release tooling built on it (`cargo xtask`). See "Updates" below and [RELEASING.md](RELEASING.md).

**`app`** is the GPUI binary. `AppView` is the root: it shows the welcome on a first run, the sign-in screen until there is a session (wuapi; the demo data needs none), then `Shell`, and the sign-in again after "Sign out". `Shell` is the main view: account rail, chat list, conversation, and what opens over them (the two menus, "New chat", "New group", the contact and group panels, a number's own profile, Settings). Preferences (theme, motion, notification choices, "welcome seen", whether updates are looked for) are a small `settings.json` in the data directory. What the emoji picker remembers is an `emoji.json` beside it. Both lists are virtualised (`uniform_list` for chats, `list` for messages, bottom-aligned). Colours, sizes and fonts live in `theme.rs` as tokens for a light and a dark palette; they follow the wuapi design system, and the logo, icon and fonts it needs are compiled in from `crates/app/assets` (`ASSETS.md` there lists origin and licence). UI tests drive the real window headlessly with clicks and key presses.

## Status (stories)

A status is a text, a picture or a video that its author shows for a day. It is optional for a provider (`Capabilities::story_*`, eleven flags, each answering `Unsupported` by default) and one of the places the client says "not available yet from this provider" instead of failing.

- **Where it lives.** Status is a destination of its own, reached without looking for it. The rail has two buttons under the logo, Chats and Status (Alt+C and Alt+S, said when pointed at), the one that is showing marked with the accent on the rail's edge, and a dot on Status while something is new. And the chat list wears a strip above its rows (`ui/status_strip.rs`): "My status" first, with a "+" to post, then everybody with a story not seen, their picture in its ring and their name under it; a click plays their status. The strip scrolls sideways and builds only the cells in view, folds to one line that counts who is new (kept in `settings.json`), and is there whenever the provider has stories at all; with nobody in it, it says why in a few words. The list's header is a title, not a second way in. The three panes stay three: with Status chosen the list pane lists updates and the main pane shows the viewer, the account's own status, or a page that says what Status is. Going back to the chats leaves them as they were. The start screen says the keys.
- **When it is asked for.** The stories the store holds are drawn in the first frame. The provider is asked when the window opens, when a number reconnects, whenever the user goes to Status (unless it was asked in the last fifteen seconds: `STORIES_OPENED`), and by whatever the provider does on its own (the wuapi adapter's poll). Going to Status, or "Check again" (`R` on the list), also tells the provider to forget that the part was missing (`Provider::recheck`), so nobody waits for its memory to run out.
- **What the list says when nobody is in it** (`Updates`, from `SyncEngine::story_listing` and the account's connection): the list is on its way, the number is offline, the provider's backend does not have contacts' updates for this number yet (with "Check again"), the last question was not answered (with "Check again"; never as a problem), the provider never has them, or nobody posted in the last day ("Updates from your contacts in the last 24 hours appear here", with "Post a status"). The account's own status stays the first row above it.
- **The list** (`ui/status.rs`): "My status" (its latest story, how old it is and how many saw it, or "Add status"), Recent updates (authors with a story not seen), Viewed updates, and the muted ones folded under a heading. A name is the one every view uses (the store's people resolver). Up and Down move, Enter opens, `M` mutes, `U` unfolds the muted.
- **The ring** (`ui/story_ring.rs`): around somebody's picture, one piece per story, oldest first from the top, the new ones in the accent and the ones seen in the rule colour. The accent (a signal, like an unread count) is used rather than the person's own colour, because people's colours say who wrote what and a ring that said both could not be read. The chat list's rows and the conversation's header wear it too, drawn outside the picture so nothing moves, and a click on it watches the status.
- **The viewer** (`ui/status_view.rs`, state machine in `stories.rs`): a segment of progress for each story of the author; a text or a picture stays five seconds, a video or a voice note its length (at most 30 s, 10 s when unknown); Space or a held pointer pauses; Left and Right move between stories, Up and Down (or Ctrl+Left and Ctrl+Right) between authors; Escape closes (first leaving the reply field). The clock only runs while the story's content is on screen and nothing holds it (the pointer, Space, the reply field, a panel).
- **Text stories** are drawn on their colour in white. WhatsApp numbers eight fonts and none is bundled here, so each maps to the nearest of Inter, JetBrains Mono and the system's serif: 0 Sans, 1 Serif, 2 Script (Inter italic), 6 Bold, 7 Capitals (Inter bold, upper case), 8 Typewriter (mono), 9 Rounded (bold italic), 10 Display (bold serif). The composer shows each in its own face, so a story reads the same on the way out as coming in.
- **Pictures** go through the pipeline of the chat's pictures: fetched as "Download media automatically" says (on a click under "Nothing"), with their progress, oriented by their EXIF. **Video plays in the viewer** (see "Video"). Until its file is here it is a tile labelled Play; it counts as seen when a frame is on screen, not when the tile is. A video in a chat still opens in the system's player. A GIF downloads with the pictures and still opens there on a click.
- **Seeing is behaviour toward other people.** A story counts as seen, and its author is owed a view receipt, only when it was drawn in the viewer: never because it was listed, prefetched or downloaded. A receipt goes out only while Settings > Sync > "Send read receipts" and "Status view receipts" are both on; with either off, viewing is local only. A receipt is queued (`story_receipts`), retried through drops, dropped if receipts are turned off before it leaves, and sent once.
- **What is fetched ahead.** The first story not seen of up to twelve authors, when it is a picture, a sticker or a GIF and the media policy fetches those by itself. Never a video that is not a GIF, and never anything that counts as seeing.
- **Replying and reacting.** A reply is a message to the author that quotes the story: it is queued in their chat like any message (same client id on every retry) and the outbox hands it to `Provider::reply_to_story`; a reaction goes to `react_to_story` the same way. In the conversation the reply wears a block that shows the status while it is there (its picture, or its words on their colour) and "Status no longer available" after, in a box of the same height.
- **Posting** (`ui/status_post.rs`, `sync/stories.rs`): a text with a colour and a font, or a picture or video from the system's dialog, a paste or a drop on the sheet, with a caption. Who will see it is said first ("My contacts", "My contacts except", "Only share with") with the way to change it, read-only where the provider cannot. A post is written to the store at once and shows under My status; its own outbox (`story_posts`) uploads the file under a key that is the same for every attempt and posts under the client id, so a drop never posts twice and never shows as a failure; only a refusal or twelve hours without success fails it, visibly, with Try again and Discard.
- **My status** (`ui/status_mine.rs`): each story with its age and what is left of its day, who saw it and when with their reactions, Watch, Forward and Delete; forwarding is the engine's `forward_story`, which treats the story as the message it is and follows the rules of forwarding a message: its words go as a text with the mark, a picture, a video or a voice note goes by naming the story (`Provider::forward_messages`, behind `forward_any`), and where the provider cannot the sheet says "Not available yet from this provider". Delete (asks first; local at once, told to the provider through drops, put back if it refuses).
- **Storage** (schema v11, only new tables): `stories`, `story_viewers`, `story_mutes`, `story_privacy`, `story_posts` with `story_post_files`, and `story_receipts`. A story and the media cached for it go 24 hours after it was posted: the engine's worker sleeps until the next deadline (no polling) and cleans up at startup too. At most 600 stories are kept per account. A text story's colour and font that the provider cannot read back are kept from the post. A database is deleted at sign-out, and removing an account removes its stories.
- **The fields that are written in** (the reply under a story, the words and the caption of a post) are "the field being written in" while they are in hand (`Shell::status_writing`, behind `Shell::writing`): a `:shortcode` is offered its emoji over the field, and the emoji picker opens for the field from its button or Cmd or Ctrl with E, emoji only, and gives back what was under it (the story, which waits meanwhile, or the post sheet with what was written). Nobody is listed behind `@`: that list is a group's participants, and a field of Status is not written in a chat (a story's own mentions would need a list of contacts, which is not there yet).
- **The conversation behind Status is out of reach.** While Status is in the conversation's place, the keys of a chat (`When::Chat`), attaching and the picker of stickers and GIFs do nothing, and the palette says "Show the chats first": nothing is sent to a chat that is not on screen.
- **Mutes** are local at once and told to the provider when it keeps them (`story_mute`); where it does not they stay here. A provider that can read a mute made on the phone and not write one (wuapi) says it as an event (`StoryMuteChanged`), which is applied whatever the flag says.

## What a backend does not have yet

A provider's capabilities say what it is built to do, and are read once. What its backend actually has can lag behind: a deployment from before a route existed, or a part that is turned on one number at a time. That is not weather (retrying does not help) and it is not a failure of anything the user did. The provider says it through `Provider::unavailable(account, Feature)`, where `Feature` is one of `ForwardAny`, `StickerFavorites` and `Stories`; it learns it from its backend's answers, answers `Unsupported` without a request meanwhile, and asks again by itself after a while (the wuapi adapter: ten minutes).

The engine and the views take it as "not available yet", for that number, for now:

- `SyncEngine::capabilities_for(account)` is the capabilities less what is missing; a view of one number asks that (`Shell::caps_now`), so nothing is offered that would answer "not available yet".
- **Forwarding**: a picture's Forward entry is off with "Not available yet from this provider"; a text is sent again with the mark, as before. A copy already queued when the backend says so is settled the same way: a text goes as a text under the same client id, anything else fails with that sentence.
- **Favorite stickers**: the Favorites section says "Your phone's favorites are not available yet for this number"; stars made here stay, nothing is retried in a loop, and they go over by themselves when the number has them.
- **Status**: contacts' updates say they are not available yet for the number under the account's own status, which keeps working (posting, listing, taking down), with "Check again": that, and going to Status, make the provider ask its backend again at once (`SyncEngine::look_at_stories`, `Provider::recheck`) instead of waiting for it to do so by itself.

When that changes, the store announces it (`StoreChange::Library`, `StoreChange::Stories`), so the line comes and goes without anybody asking. Nothing here is shown as a problem.

## Living with a bad network

Connections to WhatsApp drop; that is normal, not exceptional. The design keeps drops away from the user:

- **Sending cannot lose or duplicate a message.** The UI writes the message and its pending bubble to the store in one transaction and returns. The outbox worker then hands it to the provider with a client-generated id that the provider must treat as an idempotency key. A timeout, a dropped connection, a 5xx or a rate limit is transient: the message stays pending and is retried with backoff, with the identical request. Only a rejection by the provider, or not getting through within `OutboxConfig::max_age` (12 hours by default, kept below the provider's 24-hour idempotency window), marks it failed. After a crash, whatever was mid-flight is queued again.
- **Order is kept per chat.** A message waiting to be retried holds back later messages of the same chat.
- **Every network wait is bounded.** Provider calls run under a deadline; an overrun counts as transient.
- **A dropped stream resumes by itself.** The wuapi adapter reconnects inside the same `EventStream` with `Last-Event-ID`, so a short drop costs the engine nothing: no resubscribe, no refresh, no gap. Only a `reset` (the gateway no longer has the gap, after about thirty minutes) ends the stream, and then the engine does what it always does: subscribe again and refresh once. With no stream on the deployment the adapter polls, and the key goes only to the API and the stream origins, never along a redirect.
- **Work resumes on events, not on polling loops.** Queueing a message or an account coming back wakes the outbox; the only timer is the one for the next retry.
- **Statuses only move forward.** A late "delivered" never undoes a "read", and a message that arrives both through an event and through a send receipt is one row (matched by client id).

## From Enter to the ticks

A message sent from here goes through five states (`DeliveryStatus`), and its bubble shows which:

| State | Means | Tick |
|---|---|---|
| `Pending` | Written here; no request for it has been answered | Clock |
| `Accepted` | The provider has it and will put it on WhatsApp (queued, paced, or waiting for the number to reconnect) | One faint tick |
| `Sent` | WhatsApp has it | One tick |
| `Delivered` | It reached the other phone | Two ticks |
| `Read` | It was read | Two ticks in the accent |

`Failed` (an alert, with the reason) can follow `Pending` or `Accepted`.

- **The clock goes when the provider answers**, not when the message is on WhatsApp: the answer to the send carries the provider's id and status, and both are written to the row the bubble already is (`Store::outbox_complete`). A provider that only queues answers `Accepted`.
- **One bubble, whichever copy comes first.** The provider's copy can arrive through an event or a page of history before the request for it is answered (a slow request, or one whose answer was lost). It is matched to the waiting row by client id; the row takes the provider's id and status, and the message leaves the outbox at that moment (`outbox::settle_tx`) instead of waiting for a retry to be told the same. What waited behind it in its chat goes at once. An answer that arrives later changes nothing, whatever it says.
- **A request that timed out is not a failure.** The bubble keeps the clock, the identical request is repeated after the backoff (two seconds the first time), and the provider answers it with the message it already has.
- **After that, the provider's events move the ticks.** How promptly is the provider's business: one with a push channel hears each change, and so does the wuapi adapter while its stream is live; when it polls instead (`--live polling`, or `auto` where there is no stream) it asks (see [PROVIDERS.md](PROVIDERS.md), "Live updates: wuapi Streams" and "Following a sent message").
- **Ticks that moved while nobody listened.** At every refresh (a start, a stream that ended), the conversations that were read here before and have messages of the account's own from the last six hours that are not read yet get their newest page read again.
- **A change of the status alone is a change.** Every status that moves writes the row and announces `StoreChange::Messages` for its chat; the window reads the chat's rows again and repaints, and the tick is drawn from the row as it now is. (A row's signature, which decides what the list measures again, leaves the status out on purpose: a tick changes no height.)
- **It is measured.** The store keeps, for the last 200 sends, when each was queued, when its first request left and how many there were, how long the answered request took, and when each tick was first reached (`send_timings`, schema v8; nothing of the message itself). `wuapi-inbox --provider wuapi --diagnose sends` prints the last twenty as durations since Enter, read from the database beside a running application without changing it; the same moments are logged at debug level (`RUST_LOG=client_core=debug`), without text, numbers or keys.

## Threads

The UI runs on GPUI's executor. The engine runs on a small Tokio runtime owned by `main`. They share nothing but the store (thread-safe) and its change notifications (a broadcast channel that any executor can await). UI actions such as "send" or "mark read" are synchronous store writes plus a wake-up; they return immediately.

## Dependencies worth knowing about

- GPUI comes through [`gpui-kit`](https://crates.io/crates/gpui-kit), which pins a matching snapshot of GPUI (published as `gpui-pre`) together with the `gpui-component` widget library. The text fields, scrollbars and icons are from `gpui-component`; the layout, bubbles and lists are ours. The official `gpui` crate on crates.io is 0.2.2 from October 2025, and current `gpui-component` releases no longer build against it.
- `wuapi`, the generated Rust SDK of the wuapi API, from crates.io. The adapter turns the SDK's own retries off, because retrying is the engine's job.
- `cpal` for audio output. On Linux it links ALSA, so building needs the ALSA development headers (`alsa-lib` on Arch, `libasound2-dev` on Debian and Ubuntu); PipeWire and PulseAudio are reached through their ALSA plugins at run time. macOS (CoreAudio) and Windows (WASAPI) need nothing installed. `symphonia` and `opus-decoder` are pure Rust.
- `rusqlite` with the bundled SQLCipher (FTS5 included) and a vendored OpenSSL for its cipher, so no system library is needed on Linux, macOS or Windows; building it needs `perl` and `make`. `reqwest` with rustls (shared with the SDK, and used directly for the sign-in and media downloads). `keyring` for the API key and the database key.

## History

The chat list never waits for history: chats arrive with their last message, so the list is complete after the accounts and the chat pages. What else is fetched is a setting (Settings > Sync, `HistoryMode` in the engine):

- **When I open a chat** (default): a chat's newest page is fetched when it is opened, older pages as the user scrolls back. Opening shows what the store has at once and fills in from the network.
- **Recent chats**: the newest page of the N most recent chats of each number (20 by default), in the background.
- **Everything**: every page of every chat, in the background.

The background loader runs newest chats first with at most four requests in flight, their starts 250 ms apart (at most 240 a minute; wuapi allows 600 per key). A 429 is waited out for its `Retry-After` and the request repeated. A dropped connection ends the pass with what was fetched kept; it runs again with backoff, and at once when an account reconnects. It is cancelled with the engine (sign-out). In every mode, a chat whose history was already loaded and that has a newer last message gets its newest page fetched, so a conversation read before has no hole.

## Interface size

Every size the views use comes from `theme.rs`: the tokens in `theme::metrics` (functions, named like the constants they replaced) and `theme::px` for the sizes a view writes itself. Both multiply by one interface scale, chosen in Settings > Appearance > Interface size (80, 90, 100, 110 or 125 %) or with Ctrl and `+`, `-`, `0`, and kept in `settings.json`. The component library's rem size follows the same scale, so its paddings and gaps do too. Rules between panes stay one pixel (`theme::hairline`), and pictures in a conversation follow the scale only between 90 and 110 % (`theme::media_px`).

The chat list takes about 30 % of the window, between 266 and 323 design pixels, until its edge is dragged (228 to 494, never leaving the conversation less than 342); the width is kept in design pixels, so it scales with the rest, and a double click on the edge lets it follow the window again.

## The account rail

The rail's arrangement is the user's own and local: the order of the numbers, the groups they are in (a name, a colour, open or closed), and how each number looks (a name of the user's own, an emoji or initials on a colour, a picture, notifications muted here). It lives in `rail.json` next to `settings.json`, keyed by provider and account id, so it belongs to no provider and outlives a sign-out; when a session's numbers are known, those that no longer exist leave the file (`RailLayout::reconcile`). A picture chosen for a number is the exception: it is kept in the encrypted database (table `avatars`, under the account), so it goes with the database at sign-out.

`crate::rail` holds the decisions, with no drawing in it: `RailLayout::apply` is what a drop does (between two items: move there; onto a number: the two become a group; onto a group: join it; a group left with one number dissolves), `hit` says which drop the pointer is over (the middle half of a row is "onto", its edges are "between"), and `DragState` says when a press has become a drag (5 px) and what Escape does. The context menu and the keyboard (Alt with an arrow on a focused item, the menu key or Shift+F10 for its menu) make the same moves through the same functions. `ui/rail.rs` draws it; `ui/rail_menu.rs` is the menu and its cards.

Every item of the rail is one cell (`RailGeometry` in `ui/rail.rs`): a number is a circle in it, a closed group a rounded tile of exactly the same footprint with its members' faces two by two (up to four as they are; with more, the first three and a "+N"). Counts and lights are placed against the cell, so they line up down the rail whatever the item is. An open group is a container around a head and its numbers at full size, with the same room on every side. Items carry the room above them as a margin rather than as the column's gap, which is what lets room open between two of them from nothing during a drag.

What moves, and for how long, is in `motion::rail`: a dragged item lifts (a copy 6 % larger follows the pointer from where it was grabbed, its slot stays as a dashed outline), the others part where it would land (140 ms), a group folds open or shut (180 ms), a dropped or cancelled item settles (160 ms), and a closed group a drag rests on opens after 500 ms. A ticker repaints each frame only while something moves or is held; it is also what scrolls the rail while a drag stays near an edge. Under reduced motion every one of these is instant.

By default a number shows its own WhatsApp picture, asked for like any contact's (the picture route with the number's own id); without one, its initials.

## Pictures and media

Profile pictures and message media are fetched lazily and kept in the encrypted database (tables `avatars` and `media_cache`), never as files next to it; they go when the database goes (sign-out, reset).

- **Asking is drawing.** The chat list and the message list are virtualised, so only rows near the viewport are drawn, and a row that is drawn is what asks for its picture or image (`ui/media.rs`, `MediaShelf`). Nothing is fetched for rows nobody looks at.
- **Pictures** (`SyncEngine::want_avatar`): a chat list that carries each chat's picture id (`Chat::picture_id`) decides: the picture is fetched when that id is not the one held, never while it is, and the stored copy is dropped when the id goes away. Without an id the provider is asked at most once a day per chat, with the id of the picture already held, so an unchanged picture costs one small request and no download. "No picture" is remembered like a picture. Requests share the history preloader's pace (250 ms apart) and concurrency (four), wait out a 429, are not made while the number is offline, and never sit on the send path. Stored at 96 px.
- **Images and stickers** (`want_thumbnail`): three downloads at a time, newest request first, at most 24 waiting (older ones were for rows that scrolled away) and all of them dropped when the chat is closed. Only http(s), only what declares itself an image, at most 25 MB, refused from the response headers when they already say otherwise and cut off at the limit when they do not. This holds for every URL, whatever the host and whoever sent the message. The file is decoded behind dimension and memory limits and re-encoded as a thumbnail of at most 720 px: what is shown is always an image this process made.
- **Stickers and GIF files that move.** An animated WebP or GIF (told from its content) is the one file kept as it came: up to 8 MB, in the encrypted cache under `anim:<url>`, stored by the same download that makes its first frame (`thumb:<url>`). A picture that does not move gets an empty entry there, so the question is asked once; a sticker cached before this existed is asked about once, when its row is drawn (`want_animation`), where pictures are fetched by themselves at all. Its frames are decoded on the blocking pool behind limits (`client_core::AnimationLimits`: a 2048 px canvas, 240 frames, 24 MB of pixels at no more than 320 px a side; an animation that would not fit is made smaller before any of it is left out) and are pixels this process made, like every other picture. The open chat holds at most 96 MB of them: one that has not been painted for two seconds makes room, and when all are being looked at the newcomer stays a still picture. Leaving the chat lets them all go.
- **What moves, moves only while it is looked at.** The row paints the frame that is due (`ui/bubble.rs`, `animation.rs`) and asks for one repaint of the window when the next is, never sooner than 30 ms (`motion::animated`): the earliest request of all painted rows is the one timer there is. A row that is not painted (scrolled away, another chat) asks for nothing, so with nothing animated on screen nothing repaints. An animation holds its frame, and goes on from it later, while the window is in the background, something lies over the conversation, or its row is in the list's margin outside the viewport. Under reduced motion (Settings > Appearance > Motion) nothing is decoded and the first frame is shown, in the viewer too; `--motion-at` holds every animation at that moment. It loops for ever, as on WhatsApp.
- **A GIF on WhatsApp is a video** (a short H.264 MP4 flagged to loop silently), and it is not decoded in the chat. A video the provider flags (`Media::gif`) is a video tile with a GIF badge, and reads "GIF" in the chat list. Under "Images" it is downloaded as a picture is (up to 25 MB, not after it was stopped, not under "Nothing"); a click still opens it like any video. See "Video" below for what playing it inline would take. A vector sticker (Lottie, `application/was`) is a tile that says it cannot be shown, and is not downloaded.
- **Files still on WhatsApp.** A provider may hold only a reference to a received file and fetch it on first use (wuapi's on-demand media). The engine does not care: `fetch_media` either answers the bytes, fails for now (asked again 30 s later at the earliest, when the row is drawn again) or fails for good (the tile says why, for example "WhatsApp no longer has this file.").
- **What is not here yet says so.** A picture that will not be fetched by itself (the policy is "Never", or the message says it is larger than 25 MB) shows a round download button in the middle of its box, with the size when the message carries one; a click fetches that one, up to 200 MB. While anything loads, by itself or on a click, the button is a ring (as much of it filled as has arrived, when the size is known) and a click stops the download. A refusal turns it into "try again", with the reason; a file WhatsApp no longer has shows "no longer available" and no button. A dropped connection is none of these: the ring stays and the download is tried again. Video and document tiles carry the same button in place of their glyph (`ui/transfer.rs`); the box keeps the picture's proportions when the message gives its width and height.
- **Other files** (video, audio, documents) are tiles with "Download and open": fetched on the click (up to 200 MB) and handed to the operating system's application for the type. A GIF is the exception to the wait: it is fetched with the pictures, and the click is what opens it. That open is the one time data leaves the encrypted store: the file is written to a private directory under the system's temporary one, which is emptied at the next start and on sign-out. Nothing is ever opened without a click.
- **Voice notes and audio** (`crates/app/src/audio.rs`) are fetched on the first press of play (or ahead, under "Everything"), decoded off the UI thread and played through the system's output: Ogg/Opus with a pure-Rust Opus decoder (`opus-decoder`), MP3, AAC/M4A, Vorbis and WAV through `symphonia`, sound through `cpal`, whose own thread pulls the samples; the UI only reads the position back. One clip plays at a time, the next consecutive voice note follows by itself, and closing the chat or signing out stops it. The device is opened when something plays and released when it stops. The waveform and the length come from the decoded samples and are cached with the media; before that the bubble shows a flat line and no length. At 1.5× and 2× the voice keeps its pitch (`crates/app/src/stretch.rs`): the clip is laid down in overlapping 30 ms pieces at their recorded pace while the place they are taken from moves faster (WSOLA), each piece taken from where it continues the one before it best, then brought to the device's rate and channels. The device's thread owns all of it, allocates nothing and takes no lock; the interface reads the place (in the clip's own time, so the waveform's cursor is right at every speed) and sets the speed through atomics, so a change of speed takes effect at the next piece without a gap. The speed last used is remembered (`voice_speed` in the settings). Audio longer than 30 minutes is not decoded in memory; it opens with another application.
- **No jumps.** An avatar has the size of its placeholder. An image's box is decided the first time its row is drawn (its own proportions if the thumbnail was already cached, a 300×200 box otherwise) and kept; the image is fitted inside. Stickers are 160 px and have no bubble.
- **Budget.** The media cache holds 500 MB (`SyncConfig::media_budget`); beyond it the entries used longest ago are dropped.
- **Settings > Sync > Download media automatically**: Images (default: pictures, stickers and GIFs), Never (a click loads each), Everything (files too).

## Every kind of message

A bubble draws what the neutral model says a message is (`MessageContent` and `Message::extras`, see [PROVIDERS.md](PROVIDERS.md)); the tiles are in `crates/app/src/ui/tiles.rs`.

- **Text** is read by `markup.rs`: `*bold*`, `_italic_`, `~strike~`, `` `mono` ``, a block between triple backticks, `> quote`, `- item` and `1. item`. Links (http, https, `www.`) are clickable and open in the system's browser; nothing else is ever handed to it. A mention shows the person's name (see "People" below), the account's own reads "@You" on a wash of the bubble's accent, and one nobody can be named for reads "@someone": the digits of an id are never shown. One to three emoji on their own are drawn large.
- **A place** is a tile with its name, address and coordinates, and "Open in maps" (OpenStreetMap, in the browser). No map is drawn: that would fetch tiles from a third party just because a chat was opened.
- **Contact cards**: name, number, initials, "Message" (the chat of that contact when the address book has it, else the same path as "New chat": the provider is asked whether the number has WhatsApp) and "Copy number". Several cards are a list of three with "View all".
- **A poll**: the question, each option with its bar and count, the account's own choice, how many voted. A click votes through `SyncEngine::vote_poll`: the store shows the vote and the moved tally at once, the provider is told in the background and asked again while the failure is transient, and a refusal puts the previous vote back and says so. "New poll" in the conversation's menu writes one; it is sent through the outbox like any message.
- **A calendar event**: title, time range in this computer's timezone, place, description. "Add to calendar" writes an `.ics` file to the private directory of opened files and hands it to the system, on the click only (`calendar.rs`).
- **A link's preview** is drawn from what the message carries. The page is never fetched.
- **A view-once file** is a tile that says to open it on the phone. It is never downloaded, by any path: not as a thumbnail, not ahead of a click, not as the next voice note.
- **Notices** (somebody joined, the group was renamed, a missed call) are centred lines on the page, and do not count as unread.
- **Forwarded** (and WhatsApp's "Forwarded many times", from the fifth forward on, with two arrows), **starred** and **edited** are marks on the bubble; a deleted message is a placeholder with nothing of what it was.
- **Anything else** is a neutral "Unsupported message" tile that names the type.

Each kind also reads in one line (`client-core/src/summary.rs`): the chat list's preview and the quote in a reply. The demo data has one of each in the group "Lisbon trip".

What rides along (`extras`) is a JSON column of `messages` (schema v5), empty for most rows.

## People

WhatsApp names one person by their phone number in one place and by a hidden-number id in another: the address book lists a contact by number, a group may list the same person by hidden-number id, and a mention's text carries the digits of whichever id the sender's phone used. The store keeps the ids of one person together (schema v7): `identities` holds, for every id, the key it shares with the person's other ids, as the provider's address book last said they belong (`Contact::alt_ids`; an id that moves to another contact leaves the first), and `seen_names` holds the profile name and username each sender's own messages came with, the newest one (filled by the migration from the messages already stored, then by every message that arrives).

Everything that shows a person asks the same resolver (`client-core/src/store/people.rs`, `Store::person`), so a name reads the same in a group's sender line, a mention, a reply's quote, a notice ("Ana added Luis"), the chat list's "Name: text", search results and the participant list. The order:

1. the name saved in the address book (or a business's verified name), under any of the person's ids;
2. the name the group's participant list gives them, in that group;
3. the profile name on their own messages (then the address book's copy of it, then the title of their direct chat);
4. their username;
5. their phone number, written as people write it (`client_core::phone::format`);
6. nothing: the view shows "someone".

Names are resolved when the store is read, never written into the messages. So a name that becomes known later (the address book finishes syncing, the person sends a message) is on the rows already drawn: a change to contacts or groups makes the window read its messages and its chat list again.

**Mentions** are tied to the text by the people the message lists, never by guessing from an `@` and digits (`client-core/src/mentions.rs`): for each listed person, the digits of every id they go by are looked for after an `@`. One the text does not carry under any of them takes, in order, a stretch that looks like a mention and belongs to nobody, but only when there are exactly as many of those as mentions left; that pairing is shown and never stored as a link between ids. Text that merely looks like a mention stays as typed.

**Mentioning from the composer**: `@` in a group lists its participants (the arrows move, Enter or Tab picks, Escape closes); the pick puts the name in the text. What is sent names the person the provider's way (`Provider::mention_handle`: on WhatsApp the digits of the id) with the ids riding along (`OutgoingMessage::mentions`, behind `Capabilities::mentions`). A name typed by hand, or edited after the pick, mentions nobody (`mentioning.rs`).

## How a conversation looks

Everything below is tokens in `theme.rs` (colours per theme, sizes as functions of the interface scale) and is measured in the headless window by `crates/app/src/ui/tests/design.rs`; the contrast of every pair that carries text is a unit test next to the tokens.

- **People have a colour.** Nine of them (`Palette::sender`: lime or olive, amber, orange, rose, pink, purple, indigo, blue, cyan; no green). A person's colour comes from the key that stands for them under all of their ids (their number when it is known, else the first id: the same key the store's `identities` uses), hashed with FNV-1a, so it is the same on every run and does not change between a phone id and a hidden-number id (`ui/senders.rs`). It is the colour of their name above their bubbles, of their avatar without a picture (or the ring around their picture), of the bar and the name of a quote of theirs, of their row in a group's panel and in the `@` list, and of their name where a message mentions them (the account's own mention keeps the bubble's accent and its wash). The store is asked once per person; the answers are dropped when the address book or a group changes.
- **Runs.** Consecutive messages of one person (under any of their ids) are a run: 2 px apart, the name on the first bubble, the avatar beside the last one, level with its foot, in a column left of the bubbles. The corners two bubbles of a run turn to each other on the sender's side are tighter (4 px against 12), and the corner at the foot of the run is square: the tail, as the logo's bubble has one. A click on the name or the avatar opens the profile. An unsaved person goes by the name they gave themselves, written `~Name`, with their number after it. Chats with one person have no column and no name.
- **The account's own bubbles** come in three styles (Settings > Appearance > Message bubbles, `theme::BubbleStyle`): Brand, a quiet tint of the lime (deep olive under light text on dark, pale lime under ink on light); Lime, the lime fill under ink; Neutral, no colour. A style is a whole set of tokens (fill, outline, text, time, quote block, ticks, links, play button, the colours people are named in on it), switched by `Palette::with_bubbles`.
- **The wallpaper** (`ui/wallpaper.rs`) is one tile of the brand's devices, repeated behind the messages: crosshairs, the double tick, brackets and dots, and the outline of the mark. Two monochrome SVG layers, rasterised once into the sprite atlas at the window's pixel density and painted as one quad per tile from a single canvas; it is outside the layout, does not scroll, and its two colours are held fainter than a hairline. Settings > Appearance > Chat wallpaper turns it off.
- **Pills.** The day, the unread count and the chat's notices each stand on a small surface with a hairline (`ui/pills.rs`), so what is behind them never matters.
- **Unread.** A chat opened with unread messages shows "N unread messages" above the first of them and starts there instead of at the end. The count is what the store held when the chat was opened; messages that arrive later are not part of it, and nothing before the account's own last message is. The divider is part of the row of the message it stands above, and stays until the chat is left.
- **The header's second line** is what the other side is doing when the engine knows (typing, recording, online), else who is in the group (or how many), else the contact's number when the chat goes by a name. Nothing is said about when somebody was last seen: no provider reports it.
- **A voice note** (`ui/voice.rs`) is one row of a fixed width: a round button in the bubble's accent, the waveform, and the speed once it plays; the length and the message's time under them. The button is also the download (an arrow, a ring while it loads, a retry). Before the clip has been decoded the waveform is a row of low, even bars in the same box, so nothing moves when the real one arrives. Whether a voice note has been played is not shown: the model does not carry it.

## The keyboard

Everything in a conversation can be done without the mouse. `crates/app/src/keys.rs` is the one table of shortcuts (`BINDINGS`): a command, its keys, its name, its section and when it applies (anywhere, with a chat open, with a message in focus). The key handling resolves a keystroke through it, the menus and the palette print a command's keys from it, and the shortcuts sheet (Cmd or Ctrl with `/`, or `?` when nothing is being typed) is generated from it, so none of them can say something else. Keys are written once: "secondary" is Cmd on macOS and Ctrl elsewhere, and a chord is printed the way the platform prints it. The bindings are fixed; they are data, so a table read from the settings could replace them.

- **From pane to pane** (`ui/panes.rs`). The keyboard is in one of three panes: the rail, the chat list, the conversation. Escape in an empty composer, Ctrl/Cmd+L, or Alt+Left take it to the chat list; Alt+Left again to the rail; Alt+Right (or Right on the rail, Right or Enter on a chat) the other way. Escape never closes the conversation: closing it is Ctrl/Cmd+W. On the list a row wears the outline a message in focus wears, the arrows (or J and K), Home, End and the page keys move it, and moving it opens nothing, so walking the list reads nothing. Single keys act on that chat without opening it (P pin, A archive, M mute, U read or unread, the menu key its menu), Tab walks the filters, "/" goes to the search and any other character starts a search with it. The outline is on a chat's id, so it stays on that chat when the list is drawn again. On the rail Up and Down move between numbers and groups, Enter selects. All of it is in the registry (`When::List`, `When::Rail`), so none of it applies while a text field has the keyboard.
- **A message in focus.** Up in an empty composer, or Alt+Up at any time, gives the newest message the keyboard (`ui/thread_keys.rs`); the arrows, Home, End and the page keys move, and the list follows. The outline that says where the keyboard is is drawn outside the bubble, in a token of the page, so it reads on every bubble style and moves nothing. It stands out by the room between two bubbles of a run and no more (`metrics::FOCUS_OUT`), since the next bubble is painted after it and would cover it; and since the list paints nothing outside itself, the list keeps that room as its own padding, above its first row and under its last (`metrics::FOCUS_ROOM`, taken out of the inset above the composer, so the newest bubble is where it was). A row is never put in a box of its own for this: a row has to be what the list measures, or its height comes from a pass that lays the text out a word a line and the bubble, which stretches to its row, is that tall around one line of text. While a message has the keyboard the keyboard belongs to the shell and not to a text field, which is what makes single keys safe: a key can never be both a letter and a command. In a text field the registry's bare keys are not looked at (`keys::Context::typing`). Escape gives the keyboard back to the composer.
- **Before the text field.** GPUI runs a text field's own key bindings before any key listener, so the three things that must win in the composer (Escape giving up a reply or an edit, Up when it is empty, and the registry's chords with Cmd, Ctrl or Alt) are taken by a keystroke interceptor (`Shell::composer_key`).
- **What applies.** `Shell::command_state` is the one place that says whether a command can be run on a message: hidden when the provider cannot do it at all, off with a reason when this message does not allow it. The keys, the message menu (right-click, the arrow under the pointer, `M`) and the bar of a selection all ask it.
- **Acting on a message** is local first (`client-core/src/sync/actions.rs`): an edit, a deletion or a star shows in the store at once and is told to the provider in the background, retried through dropped connections, and put back with the provider's reason only when it refuses. A message still in the outbox is edited or taken back there. Reactions and forwards are messages of the outbox. A message is forwarded by naming the original (`SyncEngine::forward_message`, `Provider::forward_messages`, `Capabilities::forward_any`): the copy is queued under its own client id with a pending bubble of what it passes on, marked forwarded, so a retry never makes a second one, and no file passes through this client. A text the provider holds is named like anything else (it is then the original that travels, with what WhatsApp counts of its forwards); a text it does not hold (one that only this computer has, the words of a story), or any text where the provider cannot name messages, is sent again with the mark. What cannot be forwarded is refused with a reason (`ForwardRefusal`) before anything is queued, kinds a backend does not pass on included (`Capabilities::forward_polls`, `forward_events`); what the provider refuses later fails that copy alone, in the same words (the neutral codes of `client_provider::refusal`, worded by `ForwardRefusal::of_code`). A selection is forwarded in the order the messages were written (messages queued together keep the order they were queued in). The menus say why an entry is off on a second line, under its whole label. Replying and editing happen in the composer, which says which it is.
- **Selecting text.** A message's text is a participant of the window's text selection (`ui/select_text.rs` around GPUI's `StyledText`): a drag selects, across messages too, a double click takes a word, and what is copied is the text as it was written, markup included. While a message has the keyboard, Cmd or Ctrl with A selects its text.
- **The palette** (`ui/palette.rs`, `ui/palette_steps.rs`) is an editor's. Cmd or Ctrl with P (or K) opens it to go somewhere: chats, people, messages. Cmd or Ctrl with Shift and P opens it on the commands, with `>` typed. The prefixes can be typed or deleted at any time: `>` commands, `@` people, `#` groups, `/` (or `in:`) the open conversation, `?` lists them. Every command is an entry of the registry, so what is on a key or in a menu cannot be missing from it (a test walks the menus of the chat list, of a conversation, of a row, of a message and of the rail, and fails on an entry without a command). The commands of a message are listed while a message has the keyboard, by the menu's own rules. A command that cannot be run is listed dimmed, with the reason, only when it is what was typed. A command that needs to be told something asks in place: the palette stays open on a list of its own (which chat, how long, which value), Tab takes a row's name into the field, Escape or Backspace in an empty field go back one question. Enter runs; Cmd or Ctrl with Enter runs and stays. Commands are ranked by how well their name answers what was typed (the whole name, its start, its initials, a word, anywhere, its letters in order), by their keys when keys were typed ("ctrl+n", "⌘N"), then by how often and how lately they were run (`palette.json`, next to the settings). Each row shows its keys in a chip, as the platform writes them.
- **Shortcuts are written where people look.** A keyboard button in the rail and an entry in both "⋮" menus open the sheet, which is searched by typing an action or a key. Every control that is a command says its keys when pointed at (`ui/hints.rs`). The start screen and the welcome say the two keys worth knowing, the chat list's search field mentions the palette, and on a first run a tip over the composer points at it until it is dismissed or the palette is opened (`palette_tip_done`).
- **What is lifted over the window** (the palette, the sheets, the menus, the `@` list) has its own tokens: a surface, an outline stronger than a hairline, the row the keyboard is on, a slight shade. The palette and the sheets stand over a dark veil that covers the window, and a click on the veil closes them; the palette is centred in the window, its top 18 % of the window's height down, 640 px wide, and it only grows downward. When the palette or the shortcuts sheet closes, the keyboard goes back to whatever had it.
- **Search in a conversation** (Cmd or Ctrl with F) goes to the newest match as it is typed, marks what was found in the text, and steps with Enter and Shift+Enter (or Cmd or Ctrl with G).

## Emoji

One picker, in two places (`ui/emoji_picker.rs`): over the composer (its button, or Cmd or Ctrl with E), where a pick goes into the text at the caret and the picker stays open for more; and in the reaction sheet, where the six quick reactions stay and "+" or anything typed opens the rest. A reaction picked there goes the way the six do, through the outbox.

- **The data** (`crate::emoji`, `assets/emoji`) is every fully-qualified emoji of Unicode's `emoji-test.txt` (Emoji 18.0: 1923 emoji and their 2040 skin-tone variants) in the keyboard's nine groups, with names and keywords from CLDR's annotations and shortcodes from gemoji. It is compiled in as gzipped text, about 450 KB for English and ten more languages (`ASSETS.md` has the sizes and the licences). Nothing is unpacked at startup: the table is unpacked the first time a picker opens, off the UI thread, and kept for the life of the process; a language's names the first time that language is searched.
- **Search** runs off the UI thread 40 ms after the typing stops, and a newer keystroke drops the search under way. A query is matched against names, keywords and shortcodes, in English and in the search language, without case or accents ("corazon" finds "corazón"). A name that starts with the query comes before a word of a name that does, then keywords, then what only contains it; among equals the emoji people use most come first. `:fire:` and `:thumbs` look at shortcodes first, a few emoticons (`:)`, `<3`) stand for their emoji, and an emoji typed or pasted finds itself.
- **The language** is the operating system's unless one is picked in Settings > Appearance > Emoji search language (`emoji/locale.rs`). On Linux it is read from the environment as the C library reads it (`LC_ALL`, then `LC_MESSAGES`, then `LANG`, with `LANGUAGE` before them unless the locale is `C`); on macOS and Windows from the user's preferred languages (`sys-locale`). English is searched whatever it says, and a language there are no names for is English. Spanish names are Latin America's unless the system says Spain; Portuguese ones Brazil's unless it says Portugal.
- **The grid** is a list of rows (`uniform_list`): a heading or nine cells, and only the rows in view are built. What it lists is put together when the tables arrive, the search answers or a preference changes, never while drawing.
- **Skin tones**: a long press, a right click, or Alt with Down on an emoji that has them shows its tones under the grid. Picking one makes it the tone every such emoji is offered in (the first option takes it away again); an emoji of two people in two different tones is a pick and changes nothing.
- **What is remembered** is in `emoji.json` next to `settings.json` (`emoji/prefs.rs`): the 54 emoji used most with how often, the tone, the language. The most used lead the grid, as of when the picker opened.
- **Which emoji are offered** depends on the fonts. None is bundled: Inter and JetBrains Mono have no emoji, so an emoji in a text is drawn by the colour-emoji font the system's fallback finds, and a font is usually older than the newest data. The first time a picker opens, every sequence is shaped once with the text system that will draw it, off the UI thread (`emoji/font.rs`): one that comes out as the missing glyph, or as the glyphs of its parts, is left out. When even the oldest emoji do not come out whole (no emoji font, or a text system that answers differently), nothing is hidden. On Linux GPUI colours a glyph only when its font is Noto Color Emoji, and it keeps the font that has a sequence's first character without reading the variation selector, so the emoji that are text unless followed by U+FE0F and that Inter or a symbol font has (the red heart, the warning sign, the arrows, the digits of the keycaps) are drawn by that font in one colour, in the picker as in a message.
- **The keyboard** stays in the search field, so typing always searches. The keys that move are taken by a keystroke interceptor before the field sees them: the arrows walk the grid across rows and categories, Tab goes from the search to the categories to the grid, Page Up and Page Down jump a category, Enter picks (with Shift the composer's picker stays open), and Escape empties the search before it closes the picker.
- **A shortcode typed in the composer** (`:fir`, at the start or after a space, two characters at least) lists up to six emoji over the composer through the same search; the arrows move, Enter or Tab puts the emoji in its place, Escape closes the list. While the `@` list of people is open, that one has the keys.

## Profiles and groups

A contact's profile and a group's details are panels over the store, like everything else. What they show is cached in the encrypted database (schema v6: `groups`, `group_participants`, `group_join_requests`, `blocked_contacts`, `contact_profiles`, `own_profiles`) and refreshed by the engine in the background (`crates/client-core/src/sync/social.rs`):

- **Looking is what refreshes.** Drawing a panel tells the engine what is on screen (`want_group`, `want_profile`, `want_groups`, `want_own_profile`, `want_join_requests`); it reads from the provider only when its copy is older than its freshness (a group: 5 minutes; a contact's profile: 10; every group with its participants, for "groups in common": 30). Opening a group chat reads the group too. So does the provider saying it changed (`ProviderEvent::GroupChanged`, or a chat list that carries a new name for it), at once for a group somebody looked at since the application started and, for any other, when it is looked at.
- **Changes that can be put back show at once**: blocking, roles and removals, a group's name, description, settings and picture, the own name, About and picture, answers to requests to join. The engine offers each to the provider with one request id until it answers; a drop is retried with backoff, and only a refusal (or running out of attempts) puts the old state back, said in the window's problem line ("…: only admins of the group can do that", "…: the connection kept failing. Try again.").
- **What cannot be shown before it happened is awaited by its dialog**: creating a group, adding people (answered per person: who could not be added because of their privacy settings is said by name), the invite link, leaving. Three attempts, then the dialog says "try again" and keeps what was typed; the request id is kept, so a repeat creates one group.
- **A picked picture never leaves as it came.** The file dialog is the system's (the desktop portal on Linux, through GPUI's `prompt_for_paths`, so it does not hold the UI thread), behind `PicturePicker` so that tests never open one. The file is decoded behind limits, cropped to its centre square, scaled to at most 640 px and encoded as JPEG (`client_core::profile_picture`) off the UI thread.
- **Only admins are offered what only admins can do.** The group panel's Manage page, "Add participants" and the promote, demote and remove buttons need the account to be an admin and the provider to have the capability. The role comes from the participant list; when the account cannot be found in it, the role is "not known" and the controls stay, with WhatsApp deciding.

### Communities

A community is a group that links other groups, one of which is its announcement group. The model says it from both sides: `Group::community` and `Group::subgroups` on the community, `Group::community_id` and `Group::announcements` on each group it links (schema v13: two columns of `groups`). The community itself has no chat; its groups do.

- **Known without opening anything.** Every refresh ends with one listing of the groups of each connected number (`Provider::list_groups`, where the provider has `group_info`), which says the community of every group at once. A community the listing leaves out is read on its own, once, for its name (at most eight per listing); nothing is read per group. A listing that fails in passing is not a failure of the refresh, and is asked for again at the next one. The running engine lists the groups behind the refresh, so the events that queued up meanwhile do not wait for a listing that some providers read live from WhatsApp.
- **A listing is not a read of a community.** It does not say which groups a community links, so it never empties the ones a read of the community stored, and a community is still read when its panel is opened. Until then its panel shows the groups known to be in it.
- **A link or an unlink** (`ProviderEvent::CommunityChanged`) reads the community and each group it names again, at once, whether or not they were held: the chat list depends on it.
- **The chat list reads it with the chat.** `ChatSummary::community` is the community's id and name and whether the chat is its announcement group, joined in the same query as the row (`Store::chats`, `archived_chats`, `chat`). A change of a group's community, or of a community's name, announces `StoreChange::Chats`.
- **In the window.** A "Communities" filter beside All, Unread, Groups and Archived, offered only while a chat of the number on screen is in a community (and left by itself when the last one leaves). Under it the list is grouped: a row for each community (the same height as a chat row, with the community's picture, its name, "Community · N groups" and a chevron; hover, selected while its screen is open, and a keyboard stop: Enter opens the community, which has no chat), then its chats, the announcement group first and the rest in the list's own order; communities are in the order of their first chat. Only groups that have a chat are listed. The list under "All" is unchanged. A group's panel says which community it is in (a click goes to the community) and marks the announcement group; a community's panel lists the groups it links, and a click on one that has a chat opens it.
- **Managing a community.** A click on a community's heading in that view, or on the community's name in the panel of one of its groups, opens the community itself in the details panel. Its Overview lists every group it links, announcement group first, from `Provider::fetch_group` (`list_subgroups` on the wuapi provider): a group the account has a chat with opens it, one it has not is marked "Not joined" and opens nothing. Its Members page asks `Provider::community_participants` when it is opened, with loading, failed (and "Try again") and empty states, and keeps nothing. An admin of the community, where the provider has `community_manage`, can add an existing group (offered: the groups the account is an admin of that are no community and are in none, `Store::groups_to_link`), make a new group inside it (the "New group" form with the community preselected), and take a group out of it (a question first, never for the announcement group); the three call `SyncEngine::link_subgroup`, `create_group_in` and `unlink_subgroup`, which then read the community and the groups concerned again so the store and the chat list follow. The list menu's "New community" makes a community (no participants needed; it has no chat, so its panel opens). A group made inside a community may be refused by the account's engine (`not_supported`): the form says so in the provider's words and stays. Leaving a community, joining a group the account is not in, and a community's settings are not done here.

The own profile is per number: `Shell::open_own_profile(account, …)` (`crates/app/src/ui/social.rs`) opens its editor, from Settings > Account and from "Edit WhatsApp profile" in the account rail's menu. The picture it sets is kept under the same subject the rail draws a number's face from (`client_core::own_picture_subject`), so a new picture shows there at once.

Names lead to profiles: a click on the sender's name or avatar in a group's conversation, or on a mention, opens that contact's profile. Notices ("Ana added Luis") name people as the group panel does: the saved name first.

## Files on their way out

A file is sent like a text: through the outbox, and so through any number of dropped connections.

- **Queued with its bytes.** `SyncEngine::send_media` copies the file into the encrypted store (`outbox_files`) in the same transaction as the outbox row and the pending bubble. From then on nothing depends on the original file or on the application staying open. An image's thumbnail is made from that copy and cached under `thumb:local:<client id>`, so the bubble shows the picture before any network.
- **Two steps, each repeatable.** The upload (`Provider::upload_media`, under a key that is the same for every attempt: `<client id>:<round>`) and then the send, with the reference the upload answered. A failure that may pass, in either step, leaves the message pending and is retried with backoff; only a refusal (too large, a type the backend does not take) fails the bubble, with the reason. If the provider has let the upload go by the time the message is sent (`upload_expired`), the round goes up and the file is uploaded again.
- **Order.** Messages of one chat go out in the order they were written, files included: a text typed after a large file waits for it. (WhatsApp's own clients let the text overtake; here the order on screen is the order sent.) Other chats do not wait: in the background each upload runs on its own task, two at a time.
- **Progress and cancel.** The engine keeps how far each upload is (`upload_progress`); the bubble shows it, with "Cancel" for as long as the message has not been handed over as a message (`cancel_send`).
- **Limits.** A file over `Provider::media_upload_limit` is refused when it is attached, before anything is read into the store or uploaded.
- **Afterwards.** The copy moves from `outbox_files` to the media cache under `file:local:<client id>`, so the bubble keeps opening it; like any cached file it may be dropped when the cache is full, by which time the provider's own copy of the message has replaced the reference.

Attaching (`ui/attach.rs`, `attach.rs`): the "+" button opens the system's file dialog through the toolkit (`prompt_for_paths`: the desktop portal on Linux, the native panels on macOS and Windows; it does not block the interface); a drop on the conversation (or on the open sheet) and a paste in the composer end in the same sheet, which is a carousel as WhatsApp's media composer is: a large view of the file on show, its caption, and a strip of every file to pick another, take one out or add more. Enter sends them all. A paste is a picture when the clipboard holds one and no text that says something, files when it holds a file list (or, on Linux, text that is nothing but `file://` addresses or paths of files that exist, which is how file managers there hand a copy over), and text otherwise.

The caption is a composer of its own, not a plain field: the list of people behind `@`, the emoji a `:shortcode` offers, and the emoji picker (its button, or Cmd or Ctrl with E) are the conversation composer's own code, which goes by "the field being written in" (`Shell::writing`: the caption while the sheet is up, a field of Status while it is in hand, the composer otherwise), so what the composer learns the caption has. It takes several lines (Shift+Enter; Enter sends), Escape closes a list before it closes the sheet, and a file pasted into it joins the ones in the sheet. The mentions go out as mentions with the media message, and a reply that was under way when the file was attached is what the file answers (the sheet shows the quoted message). Each file has a caption of its own: a text field per file, made when the sheet is drawn (a field needs the window), with its own mentions, caret and undo history, so switching files keeps all of it; `Shell::writing` and `Shell::mentions` go by the file on show. Sending queues every file that can go through the outbox, in the order of the strip, each as a message with its own caption and mentions; the reply goes with the first one only (the sheet says so). "Send as a document" is per file, with "Apply to all". A file over the provider's limit is not read, only named: it is flagged on its thumbnail and in the sheet and holds back only itself. Files go by Ctrl or Cmd with Page Up and Page Down (keys a text field does nothing with, so the caret keeps its keys), and by the bare arrows when the strip, which Tab reaches after the caption, has the keyboard; Ctrl or Cmd with Shift moves the file earlier or later, and Delete or Backspace on the strip takes it out (all in the shortcut registry, `When::Attach`). Leaving (Escape, Cancel, a click outside) asks first when there are several files or a caption has text, and Escape again discards. The emoji picker is an overlay like the sheet, and there is one overlay at a time: while it is open the sheet is not drawn, and it comes back, on the same file with the same caret and the keyboard in its caption, when the picker closes.

## Files on their way in

Copying a picture and saving a file (`clipboard.rs`, `ui/media_out.rs`) always hand over the original: when only the thumbnail is on disk the file is fetched first, with the transfer shown on the message as for any download, and the copy or the save happens when it arrives. Nothing is re-encoded on a save, and the bytes are written only where the user said.

- **Copy image** (pictures and stickers): the message menu, Ctrl/Cmd+Shift+C, Ctrl/Cmd+C on a focused picture without text, the button on the picture and in the viewer. The clipboard is offered `image/png` and, for JPEG, WebP and GIF, the file as it came. On macOS and Windows this goes through the toolkit's clipboard. On Linux the toolkit writes text only, so there are two backends, tried in this order (`clipboard::backends`): on Wayland the data-control protocol (`wl-clipboard-rs`, which serves the data from its own thread for as long as the copy is the current one), then X11 through XWayland when `DISPLAY` is set (`arboard`, PNG only, its owner kept alive for the life of the app); on X11 only the latter. GNOME's Wayland session does not give data-control to ordinary apps, so there the copy goes through XWayland, which Mutter mirrors to Wayland clients. The toolkit gives no way to offer other types through its own Wayland connection. When no backend works the notice says why.
- **Save as…** (Ctrl/Cmd+S) opens the system's dialog through the toolkit, in the folder used last (kept in `save-folder` next to the settings; the system's Downloads at first), with the message's file name or `<chat> <date time>.<ext>`. **Save to Downloads** (Ctrl/Cmd+Shift+S) asks nothing, never overwrites (`name (1).ext`) and offers "Show in folder". With several messages selected, Save asks for one folder and writes them all there.
- **The viewer** (`ui/viewer.rs`) opens every picture whole: fitted inside the window less the toolbar and a margin, in its proportions, centred, and never enlarged past its own size. Its scale is always against the picture's natural pixels and that is what the toolbar says: 100 % is one pixel of the picture on one logical pixel of the window (two device pixels a side on a display scaled 2x). "+" and "-" walk 10, 25, 33, 50, 67, 75, 100, 125, 150, 200, 300, 400, 800 %, down to 10 % (or the fit, when that is smaller) and up to 800 %, around the middle; the wheel scales by a quarter per line around the pointer; "0" fits, "1" is actual size, two clicks toggle between them around the click. A drag moves the picture only on the axes where it is larger than its room, and only until its edge meets the room's. A fitted picture follows the window; a zoomed one keeps its scale. Left and Right walk the conversation's pictures, each opening whole. The toolbar also copies, saves, opens with the system's app and closes.
- **What the viewer draws** is the original, decoded off the interface's thread (`client_core::upright`): turned as its EXIF orientation says, so a phone's portrait photo is upright and its width and height are the ones looked at, and scaled down to 4096 pixels on its longer side at most (64 MB of pixels), which changes nothing of the natural size the scale refers to. Until it is here the thumbnail stands in, fitted to the same room, with the transfer's progress. Thumbnails are made upright the same way, so the box in the conversation has the right proportions (thumbnails made before this stay as they were).
- Dragging a file out of the window is not there: the toolkit cannot start a drag to other apps.

## Recording a voice note

`crates/app/src/record.rs` and `ui/voice_record.rs`. The microphone button is in the composer while nothing is typed (with text there it is the send button); Ctrl/Cmd+Shift+R does the same at any time. Recording is hands free: the bar takes the composer's place with a red light, "REC", the time, a live meter, and buttons to pause, stop, throw away and send. Enter sends, Space pauses and goes on, Escape throws it away (after asking once when it is longer than three seconds), and the shortcut again stops it so that it can be listened to before it is sent. Where files cannot be sent nothing is recorded: the button says why.

- **The microphone** is an `AudioInput`: `cpal`'s default input device (or the one chosen in Settings > Audio), read on the device's own thread, which only hands over what it heard. It is opened by the click and closed the moment the recording is stopped, sent or thrown away; nothing listens before. A recording thrown away is zeroed and dropped. The tests bring their own input, and the window's default input in a test build is one that refuses to open.
- **What is recorded** is brought to one channel at 16 kHz (a windowed-sinc resampler that keeps nothing above the new band), which is what the phones record a voice note at, and stops by itself at 15 minutes. WhatsApp publishes no length limit for voice notes; 15 minutes are about 2.7 MB. Under a second nothing is sent.
- **The file** is Opus in an Ogg container (`audio/ogg; codecs=opus`, what WhatsApp takes as a voice note): 20 ms packets at 24 kbit/s from `ropus`, a Rust port of libopus (BSD-3-Clause, no C toolchain), in pages written here (RFC 7845: `OpusHead` with the pre-skip, `OpusTags`, a page a second, the last one ending where the sound ends). A test decodes it with the player's own decoder, which is a different implementation.
- **Sending** is `SyncEngine::send_media` like any attachment: the bytes go into the encrypted store with the pending bubble, and the outbox uploads and sends them, through drops. The bubble has its length and waveform at once, from the samples in hand.
- **Settings > Audio** chooses the microphone and the speakers (kept in `audio.json` next to the settings) and has a level test, which opens the microphone for at most ten seconds, keeps nothing, and closes with the panel.
- **Packaging**: a macOS bundle needs `NSMicrophoneUsageDescription` in its `Info.plist` or the system refuses the microphone without asking; on Windows the user's "Microphone access for desktop apps" privacy setting must be on; on Linux the microphone comes through ALSA (PipeWire and PulseAudio by their ALSA plugins), and a sandboxed build (Flatpak) needs the audio permission. A refusal shows in the bar as the reason the device gave.

## Stickers and GIFs

One popover over the composer holds three tabs, as WhatsApp's does: Emoji (the emoji picker, embedded, not rewritten), GIF and Stickers (`crates/app/src/ui/picker.rs`, `picker_view.rs`). The composer's button opens it on the tab used last (kept in `settings.json`), Cmd or Ctrl with E on Emoji, with Shift+E on Stickers and with Shift+J on GIFs; each again closes it, and from one tab another's key changes tab. The keyboard stays in the search field, which searches whatever tab is on; Tab walks search, tabs and grid, the arrows walk the grid, Enter sends (Shift keeps the picker open), Alt with Down opens the tile's menu, and Escape empties the search before it closes. Both grids are virtualised (only the rows in view are built), their stills are read from the encrypted store when a row is drawn, and **only the tile under the pointer or the keyboard moves**, one at a time, decoded off the interface's thread; reduced motion or "Animate stickers and GIFs on hover" off keeps all of them still. The caption's picker (from the attach sheet) is emoji only, and so is that of a field of Status. While files are being attached the Stickers and GIFs shortcuts do nothing and nothing is sent from the picker: a sticker or a GIF is a message of its own, sent at once, never a file of the sheet. A `.gif` or a picture chosen from disk as an attachment goes through the sheet with its own caption and is not kept in the library.

- **The library** (`client-core`: `library.rs`, `store/library.rs`, `sync/library.rs`; schema v9: `library_items`, `library_packs`, `library_remote`) keeps files in the encrypted database, each under the hash of its bytes (the same sticker saved from a chat, imported and starred on the phone is one row), with a small still, its name, pack, source, when it came and was last used, and whether it is a favorite and where. It has a budget (64 MB): past it the items used longest ago go, **never a favorite**. It goes with the database on sign-out (tested), and "Clear" in Settings > Stickers and GIFs keeps the favorites unless "Clear all" is pressed. A file enters it by "Add to favorites" or "Save GIF" on a message (the message menu, the keys V and G, the star on the picture), by importing files (the + under the grids, or the palette), by the online search, or from the phone.
- **Stickers tab**: Recently used (what the account sent, from here or from its phone, or used from the picker, newest first, at most 36), Favorites, each pack, From your chats (received stickers, newest first, at most 120, not already above) and every sticker not in a pack. Sections with something in them come first; an empty one is its heading and one wrapped line, after them. The grid is a list of rows of different heights (a heading, a line of words, a row of tiles), of which only those in view are built. A pick is sent at once as a sticker, no caption, through the outbox like any file (copied into the store with the pending bubble, uploaded under one key, safe to repeat; as the reply when one is under way). Where files cannot be sent the strip says why instead of failing after the click. Star and unstar with Cmd or Ctrl with D or the star in the strip, reorder favorites (Alt with Left or Right) and remove from the tile's menu (right click, or Alt with Down).
- **Making a sticker from a picture** (`sticker_from_image`): a 512 by 512 WebP, the picture in the middle in its own proportions on transparent padding, at most 100 KB. The encoder is the `image` crate's `image-webp`, which writes **lossless WebP only** (a lossy one would be a C library) and has no animation writer. To fit 100 KB the colours are rounded to fewer bits, which a lossless coder packs much better, and if that is not enough the picture is made smaller inside the canvas; a picture that still does not fit is refused. **Animated sources are not converted**: an animated GIF gives its first frame (said), and an animated WebP is taken as it is when it already fits (512 per side, 500 KB) and refused otherwise. A still WebP already 512 by 512 and small enough is kept byte for byte. Several pictures imported at once are a pack named for their folder.
- **Favorites from the phone** go through three methods of the `Provider` trait behind `Capabilities::sticker_favorites` (see PROVIDERS.md). The engine reconciles one account at a time (`reconcile_favorites`): what is starred there and was not seen before is fetched and starred here, what was unstarred there is unstarred here, what was unstarred here is removed there, what is starred here and unknown there is added there. It works from what the account was known to have starred at its last run (`library_remote`: the item and the id the provider lists it under, which a backend may choose itself), is safe to repeat and runs when the account connects, when the Stickers tab opens (not more than every five minutes) and after any change here. A sticker that was seen in a message of the account names that message when it is starred there (`library_items.origin_message`, filled by the indexer and by "Add to favorites" on a message), so a provider that can star by naming a message moves no file; one that came from elsewhere goes by its bytes. A provider asked to slow down ends the run's downloads (the rest come with the next), and one that does not have favorites for the number yet ends the run quietly (see "What a backend does not have yet"). wuapi has the routes since SDK 0.12.0 and turns them on one number at a time.
- **GIFs tab** (`gifs.rs`): a backend trait with two backends. *Saved* is the library's GIFs (recent first; searched by name) and never leaves the computer. *Giphy* is **off by default**: nothing is requested, and no key is built in, until the user turns it on in Settings > Stickers and GIFs and pastes their own API key, which is kept in the OS keychain (`gif-search-key:giphy` under the application's service) and never in `settings.json`. A search is one `GET` to `api.giphy.com` with the key and the words typed; previews and the MP4 are fetched only from the service's own hosts, behind a size limit. A pick downloads the MP4, keeps it in the library as a GIF and sends it. The settings text says that searches are sent to that service. Tests play the service with a local server and check that with the switch off, or on without a key, there are no requests at all.
- **What a GIF is on the wire**: WhatsApp's GIFs are MP4 videos flagged to play as one. A saved MP4 is sent as a video with `media.gifPlayback` (`OutgoingContent::Media::gif`; wuapi takes the flag on a `video` send and nothing else), and its bubble says GIF from the start. A `.gif` file is sent as the image it is: the API converts nothing, so the other side sees a picture. Making a `.gif` loop on the other side would need turning it into an MP4, which needs an H.264 encoder (the same family of dependency as the decoder in "Video" below), and is not in this build. A received GIF is a video that says so (`Media::gif`; wuapi's `media.gifPlayback` since SDK 0.12.0), and wears the GIF badge; "Save GIF" is still offered for every MP4 and `.gif`, since a GIF sent by an older build of the backend does not say.
- **Previews**: a `.gif` or an animated WebP has a still and moves on hover. **An MP4 has no still**: there is no video decoder and the engine gives no thumbnail, so its tile is labelled ("MP4", with its name). Online previews are the service's small stills.

- **Stickers already in the chats** (`sync/library_index.rs`, schema v10). An account that never saved a sticker still has them in its messages, so an indexer reads the sticker messages in the store and lists them as library rows made by it (`indexed`), with when the account last sent each (`sent_at`, from this computer or its phone: any outgoing message) and last received it (`heard_at`) and the media reference they came from. One model, not a view over messages: recency, starring, de-duplication by the library's hash and eviction work the same for every row. Indexed rows are let go first when the library is over its budget and are pruned to the newest 36 sent and 120 received unless starred or used; a star makes one a favorite like any other and keeps it. It reads **the cache, never the network**: an animated sticker becomes an item with the original the cache keeps for it, a still one as a 512 by 512 WebP made of its cached thumbnail (the original of a still is not kept; the thumbnail is the same pixels, so the same sticker under two references is one row); one not cached yet is a place (a row with no bytes) that the picker fills in by asking for its file when its tile is built, with the conversation's own download queue and policy (with downloads off it waits for a click), and the engine completes it when the file arrives. The indexer remembers where it got to (`library_index`): new messages above a mark, old ones below another, read newest first in windows of 20 000 rows, 24 stickers a run, until the caps are met; a loop runs it off the async workers when messages arrive or a thumbnail is cached, never on a timer. A sticker sent from here is the library item that was sent, and is not listed again. Nothing here marks a chat read.
- **Starting over**: "Clear" in Settings > Stickers and GIFs removes these rows too; the indexer goes on from where it was, so they come back only as new stickers arrive.

## Video

A story's video plays inside the viewer (`crates/app/src/video.rs`). The decoder is libmpv, LGPL-2.1-or-later, loaded at runtime with `libloading`. This crate stays Apache-2.0: it never links libmpv. A release embeds one self-contained shared library, chosen with `WUAPI_VIDEO_BUNDLE` (an absolute path to a `.tar.gz` of an LGPL build, codecs linked statically, no GPL or nonfree parts). `WUAPI_VIDEO_BUNDLE_REQUIRED` fails the build when that path is missing. `WUAPI_LIBMPV_PATH` replaces the embedded copy. The application does not load a system or Homebrew libmpv on its own. Frames are software BGRA, capped at 640 on the long side, and painted into the story card. The bytes stay in the encrypted store and are streamed to libmpv; they are not written out for the operating system to open. The tile's time does not count as time in the video. A file that cannot be played says so and the story moves on.

A video in a chat still downloads on a click and opens in the system's player. A GIF tile downloads with the pictures and still opens there on a click. An MP4 still has no still for those tiles. Playing a GIF inline in a chat, muted and looping, is the same decoder and is not wired there. What was weighed for a decoder at all:

| Route | Linux | macOS | Windows | Cost |
|---|---|---|---|---|
| The system's frameworks | GStreamer or VA-API: a system dependency, and H.264 only where the distribution ships the plugins (`gst-libav`, `openh264`) | AVFoundation / VideoToolbox, nothing to install | Media Foundation, nothing to install (absent on "N" editions without the Media Feature Pack) | Three back ends to write and test behind one trait, each handing frames to the renderer; Linux keeps a run-time dependency and can still be without a decoder |
| GStreamer everywhere (`gstreamer-rs`, LGPL) | System packages | Its framework has to be bundled or installed | Its runtime has to be bundled or installed | One code path; installers grow by tens of megabytes on macOS and Windows; the first build-time system dependency besides ALSA |
| FFmpeg, bundled (`ffmpeg-next`) | Built or linked | Built or linked | Built or linked | LGPL only if linked dynamically and built without its GPL parts (no x264: decoding does not need it); a C toolchain (nasm) in every build; 5 to 15 MB per platform; H.264 patent licensing becomes the distributor's question |
| OpenH264 as Cisco's binary (`openh264` crate, BSD) plus a pure-Rust MP4 demuxer | Downloaded at run time | Downloaded at run time | Downloaded at run time | Cisco covers the patent licence only for the binary it distributes, so it must be fetched from Cisco on first use, not bundled (a download the user has to agree to, and no playback offline until it happened); whether its decoder handles everything phones produce (High profile, B-frames) would have to be measured on real files first |
| A pure-Rust H.264 decoder | | | | None is complete enough to rely on today |

Stories use the libmpv path above, loaded dynamically so the application stays Apache-2.0. Chat GIFs stay tiles. The neutral model is ready for them (`Media::gif`), and the frame-by-frame painting that stickers use (`animation.rs`, `MediaShelf::play`) is what a decoder feeds.

## Updates

[RELEASING.md](RELEASING.md) is the manual; this is how it sits in the application.

- **Where it runs.** The updater (`updater::Updater`) is a task on the engine's Tokio runtime. The window never calls it and never waits for it: it reads the last snapshot (`crate::update::snapshot`, a GPUI global), and a task on the interface's executor copies each new snapshot there and asks for a repaint. What the window can ask for (check now, restart, the switch, another source) goes through `update::Actions`, which the window's tests replace with a recorder.
- **Three moments of the start** (`update::Boot` in `main`): before anything else, an update that is ready is verified again, renamed into place and started, and this process watches it and leaves (or puts the old version back and goes on); before the store is opened, the new version notes the schema it is about to bring the database to; once the window is open, the new version says it is up, and the kept version is deleted.
- **The trust anchor** is an Ed25519 signature on the manifest by a key whose public half is compiled in (`updater::sign::EMBEDDED_KEYS`), not TLS and not the host. With only the placeholder there, the updater is off and says so.
- **What it keeps on disk**: `updates/` in the data directory (its state, the staged download, the mark of an update not yet seen to start) and `update.json` next to the settings when another source was set. It never touches the databases or the settings.
- **An older build and a newer database.** Migrations only go forward, so a build that finds a schema newer than its own leaves the file exactly as it is and runs the session in memory, saying why (`storage::newer_database`). The same rule stops an update from being undone behind a database it already migrated.
- **In the window** (`ui/updates.rs`): Settings > About (version, channel, last check, the state in a sentence, the notes, "Check now", "Restart now", the automatic switch, and the source under Advanced), a button with the rail's tools only while an update waits for a restart, and two commands of the registry, "Check for updates" and "Restart to update".

## Credentials that stop working

A 401 from the provider is not weather. The engine records it (`SyncEngine::auth_lost`), stops its loops and asks nothing more; queued messages stay queued rather than failing. The application then shows the sign-in with "This device was signed out", forgets the useless key and leaves the local data alone. A timeout, a dropped connection, a 429 or a 5xx never takes this path: they are retried.

Signing in again as the same organization and project keeps the chats on disk. Signing in as another deletes them first (the database records whose data it holds, in `<database>.owner`). "Sign out" in Settings always deletes: the API key, the database with its journals, and the database's key; settings stay. It asks first, says how many messages are still waiting to be sent, and with any waiting it takes the button, not Enter. There is no media cache yet; when there is one it belongs in the same wipe.

## The database on disk

Messages are encrypted at rest. The database is SQLCipher; its key is 32 random bytes made on first run, kept in the OS keychain (one entry per database file, separate from the API key) and handed to SQLCipher raw (`PRAGMA key = "x'…'"`), so opening costs no key derivation. The key is never logged or written anywhere else. `client-core` only takes the key; `crates/app/src/storage.rs` finds it:

- **A plain database from an earlier version** is converted in place: an encrypted copy is written next to it with `sqlcipher_export`, opened with the key to check it, and only then moved over the original; the plain file's `-wal` and `-shm` are removed. If any step fails the copy is deleted and the plain file is as it was; the session then runs in memory and says why.
- **No keychain** (`--no-keychain`, or a Linux session without a Secret Service): nothing is written to disk in clear. The session uses an in-memory database and the chat list says so. Refusing to start was the alternative; the local data is a cache of what the provider has, so a usable session that plainly says it is not saved was preferred.
- **The key is gone but the file is there** (the keychain was wiped): the application asks before doing anything. "Reset local data" deletes the file and syncs again under a new key; messages that were still waiting to be sent are lost, and the prompt says so.

In-memory databases (tests, the demo data without `--data-dir`) are not encrypted: nothing reaches the disk.

## The name

The product is "Wuapi" ("wuapi Inbox" in its first releases, a name its data keeps): binary and package `wuapi-inbox`, application id `dev.wuapi.inbox`, all from `crates/app/src/product.rs`. An install made under the working name (`fastwhatsapp`) is moved on the first start (`rename.rs`): the data directory is renamed and the keychain entries are filed again under the new service, the database keys under their new paths. The new entries are written before the directory moves and the old ones deleted after, so a failure at any point leaves a database that its key still opens. It is skipped when the new directory already exists, with `--data-dir`, or when the keychain cannot be read while there is an encrypted database to carry.
